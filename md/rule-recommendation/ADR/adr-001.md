# DQC Rule Authoring — AI Generation UX Proposal

I agree with your reasoning. Knowing that AI generation lives inside the existing **Rule Authoring/Editing modal** changes my recommendation to **Option A**.

The key is to make AI generation a **mode within the modal**, not another modal or a separate workflow.

## Why Option A Fits Better

The existing modal already represents a focused task: **authoring or editing one rule**. Switching between manual authoring and AI-assisted authoring is a natural variation of that task.

With Option B, you'd have a button that reveals another input area inside a modal that already contains multiple fields. That creates a less predictable layout.

Option A offers clearer separation:

- **Rule Name and Description:** Metadata that remains consistent across both modes.
- **Manual DQDL:** Existing code editor and validation behavior.
- **Generate with AI:** A dedicated prompt, generated preview, and explicit apply action.
- **Save Rule:** The existing persistence workflow, independent of how the DQDL was produced.

---

## One Architectural Decision I'd Make

Don't treat Manual and AI as two separate rule objects or independent form states.

Maintain **one authoritative DQDL value** and **one temporary AI candidate**:

```typescript
type AuthoringMode = "manual" | "ai";

interface RuleEditorState {
  mode: AuthoringMode;
  ruleName: string;
  ruleDescription: string;
  dqdlExpression: string; // Authoritative value
  aiPrompt: string;
  generatedCandidate: string | null; // Not saved yet
}
```

When the user clicks **Apply to Editor**, copy `generatedCandidate` into `dqdlExpression`.

Switching modes alone should never overwrite it.

### Default Authoring Mode

I'd consider:

- **Editing an existing rule:** Default to Manual DQDL and let users opt into AI.
- **Creating a new rule:** Initially preserve the existing default. Eventually, consider defaulting to AI if adoption supports it.

### Important UX Safeguard

Keep the modal's **Save Rule** button disabled or otherwise unavailable for committing AI output until the generated candidate has been explicitly applied.

The saved rule should always be the authoritative `dqdlExpression`, not an unaccepted suggestion.

---

## Final Recommendation

This is a stronger proposal to take back to your team than simply adding a Generate button.

You're defining:

1. **The interaction contract:** How users switch between manual and AI-assisted authoring.
2. **State ownership:** Which DQDL value is authoritative.
3. **User safeguards:** How AI-generated changes are reviewed before being applied.
4. **Workflow consistency:** How both authoring modes share the existing validation and persistence process.

**Key takeaway:** AI generation should be an alternative way to author DQDL within the existing modal, while the user retains explicit control over what gets saved.
